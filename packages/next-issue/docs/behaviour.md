# next-issue behaviour

This document holds the detail behind the [README](../README.md): edge cases, failure handling and internal behaviour.

## What it does

Before each issue, fetch the open issues again and take the oldest one not yet seen in this run. An issue seen once in a run is not tried again in that run while its labels stay as the first fetch after its attempt found them. When its labels change, for example once a person answers a hand-over or makes a skipped issue ready, the next fetch claims it again in the usual order. An issue that is done, or that failed with an error and was not handed over, is not tried again in that run. The run ends when no unseen issue is left. When the fetch fails, the run claims no new issue, ends once the running issues end, writes the summary of the issues it handled and exits with code 1.

`npx -y next-issue@latest start` runs the work in the worker of the repository, see [Worker](#worker). It connects to the worker, or starts one in the background (the `serve` command of the same version, with its output in `.next-issue/worker.log`) when none answers, and then starts the run there with its flags. Once the worker accepts the run, `start` prints ``the run started in the worker; follow it with `npx -y next-issue@latest logs` and stop it with `npx -y next-issue@latest stop` `` on standard error and exits with 0. It prints no output of the run and no summary, and handles no `Ctrl-C`: the run goes on in the worker whatever happens to `start`. Follow the run with `npx -y next-issue@latest logs` and stop it with `npx -y next-issue@latest stop`. A run that fails after the worker accepted it does not change the exit code of `start`; the worker writes `<reason>` to `.next-issue/worker.log`, also for a failure before the run log opens, such as a missing remote or an older git. When the worker is older than `start` and no run is going, it closes and `start` starts a new one. A newer client (such as a newer `next-issue` CLI) or a newer version on npm can upgrade the run to a newer worker; [Worker](#worker) says when and how. `npx -y next-issue@latest logs` moves on to the run log of the newer worker. `start` tells the worker its version each time it connects. When a run is going in the worker already, `start` starts no second run: it switches the run to the `--watch` and `--hunt` values it was given, as `npx -y next-issue@latest watch` and `npx -y next-issue@latest hunt` do, leaves the settings it was not given as they are, ends a wait between passes of a watching run so that it looks for issues at once and its back-off starts again from 1 minute (a run in a pass looks next as it would have), prints `a run is going already`, then the `npx -y next-issue@latest status` output, on standard error and exits with 0. After `npx -y next-issue@latest stop`, with or without `--after`, `start` fails with `the run is stopping` and the stop goes on; start a new run once it ends. When that worker is older and refuses the `start` with `a run is going in this repository already` or `the worker is restarting, try again soon` (a worker from before this behaviour), `start` switches the run there with `watch` and `hunt` messages instead; when it does not answer within 5 seconds, `start` fails with `the next-issue worker did not answer`. With an older worker, the status shows `stopping for an upgrade to <version>` while the run stops for the upgrade, as [Worker](#worker) describes. `start` does not take back a stop for an upgrade either. When the worker refuses the run for another reason, `start` prints `<reason>` and exits with 1.

Only one worker goes at a time in a repository. It holds the lock `.next-issue/worker.lock`, with the process id and the start time of that process, for its whole life. A run that the worker starts takes no lock of its own, since the worker runs at most one run at a time. When a process that does not take connections on the worker socket holds the lock for more than 2 seconds, `start` starts a worker anyway, which exits with `another worker is running`, so `start` claims no issue and exits with code 1 and the error `the next-issue worker exited before it listened: exit code 1 (see .next-issue/worker.log)`. A lock whose process is gone, or started at another time, is stale and taken over. The start time is read in UTC, so a command with another `TZ` than the worker still sees the lock held. When the start time cannot be read, the lock is held while its process is alive.

Every command uses the main worktree of the repository as its root, the first one that `git worktree list` shows, even when it runs in a linked worktree. So `.next-issue/`, with the config, the locks, the worker socket, the saved state and the notes, and `.claude/worktrees/` are always in the main worktree, and a run or worker started from a linked worktree gets the same refusal as one started from the main worktree.

A run works on up to `concurrency` issues with an agent at the same time, 1 by default. Each claimed issue takes a slot. An approved issue frees its slot while it waits to land, while it lands and while it waits for the checks on the base, so the next issue's agents never wait for CI. When such an issue needs an agent again, for example the fixer for a conflict or for failed checks, it waits for a free slot, takes it before any new issue is claimed and frees it once the agent ends. So no more than `concurrency` agents run at once. When a slot frees up, the run claims the oldest unseen issue for it, and fetches the open issues again only when the last fetch left an unseen issue unclaimed or an issue has ended since. When an issue ends while every slot is taken, the run still reads the open issues again, so the open-issue count stays current, but claims nothing until a slot frees up. When an issue ends `done` after the run has stopped claiming, because of a stop or a halt, the run reads the open issues again too, so the count shows the closed issue. The run ends only once every issue has ended, including those waiting to land. Each issue has its own worktree and branch. Step 3 below and the removal of a worktree or branch run for one issue at a time, so two issues never change the git refs or worktrees of the repository at once. An issue skipped as blocked is tried again in that run once another issue is done, so an issue blocked by one that waits to land is claimed once its blocker closes. For each issue:

1. Claim the issue only when it holds the `status:todo` label and holds no `status:in-progress` or `status:in-review` label. A `status:done`, `status:needs-human` or `status:blocked` label always stops the claim, a resume too, except a `status:needs-human` issue with an answer to its hand-over that the run made, and except an issue whose finish a stop cut short and that was not handed over (see step 7 below). An issue that GitHub lists as blocked by an open issue waits, because its blocker closes only when the change of the blocker lands. An issue with saved state under `.next-issue/` resumes instead, whatever its other labels and blockers. Right before the claim, the run reads the state of the issue again, since GitHub search can still list an issue that was closed a few seconds ago. An issue that is closed by then is dropped as a closed issue (see [Retry an issue that waits for a person](#retry-an-issue-that-waits-for-a-person)), with no label change, comment or agent.
2. Add `status:in-progress` to the issue.
3. Fetch the remote, fast-forward the local copy of the default branch when that is safe, then add a git worktree at `.claude/worktrees/next-issue-<n>` in the repository root on the `<n>` branch. The `next-issue-` prefix keeps it apart from a Claude Code worktree that a person names after the issue, such as `.claude/worktrees/<n>`, which the harness leaves as it is. An issue that resumes from saved state keeps the branch name that the state holds, and a worktree at `.claude/worktrees/next-issue-<n>` that holds that branch already stays in use. When any other linked worktree, such as a person's `../fix-<n>` or Claude Code worktree `.claude/worktrees/<n>`, holds that branch on a resume, the harness leaves that worktree, its files and the branch as they are: the issue fails and is handed over, and the reason names the path of that worktree and asks you to check out another branch there. Once you do, the next resume opens `.claude/worktrees/next-issue-<n>` on the branch, with your commits. A branch that exists on the remote is the start, and a local branch that fell behind the remote is fast-forwarded; a local branch that cannot be fast-forwarded stays as it is and the harness writes a `branch.behind` event. The fetch prunes remote branches, so a remote branch that was deleted does not count. A local branch that the remote does not hold and that has no commits of its own starts again from the remote base. An issue with no saved state does not reuse a local `<n>` branch: it resets that branch, and its worktree at `.claude/worktrees/next-issue-<n>` when that holds it, to the remote branch, or to the remote base when there is none. When that local `<n>` branch has commits that the remote branch, or the remote base, lacks, such as a person's unpushed commits, the harness first keeps them on a `<n>-kept-<sha>` branch, so no commit is lost. When any other linked worktree, such as a person's `.claude/worktrees/<n>`, has the `<n>` branch checked out, the harness leaves that worktree, its files and the branch as they are: the issue fails and is handed over, and the reason names the path of that worktree and asks you to check out another branch there. The harness does not remove that worktree, and until the issue first opens its own worktree, a retry after an answer counts as a new issue, so it is refused again while that worktree still holds the branch. A worktree at `.claude/worktrees/next-issue-<n>` left on a detached HEAD or on another branch, for example by a crash, is removed, but its uncommitted and untracked files are first committed on a `<n>-detached-<sha>` branch, so they are kept. A commit on that detached HEAD that no branch or other ref holds is kept on that branch too. When the main worktree of the repository has the base branch checked out, the harness fast-forwards it there with `git merge --ff-only` when that is safe, which changes the files there. Otherwise the main worktree is never used, reset or cleaned: when it has the branch of the issue checked out, the issue fails and is handed over, and the reason asks you to check out another branch there. A fast-forward of the base that is not safe leaves the local base branch as it is and writes a `base.behind` event. A new branch then starts from the remote base.
4. Let the implementer agent do the work, then commit it. For a behaviour change, the implementer writes the test first and quotes its failing output in its reply. The harness keeps that reply in the state file for the reviewer. After every commit on the `<n>` branch, by the implementer, a fixer, the merge of the base or the squash, the harness pushes the branch to the remote with `--force-with-lease=refs/heads/<n>:<sha>`, since it rewrites the branch, so the work is not lost with the machine. `<sha>` is the commit the harness last pushed to `<n>`, saved in the state file, or for the first push the commit of the remote branch when the worktree opened (or no branch). When a run resumes the issue and step 3 fast-forwards the branch to commits someone else pushed to `<n>`, `<sha>` becomes the commit of the remote branch. When the resume instead puts the branch back at a commit saved before a stop during a review, a squash or a revert, which drops those commits, `<sha>` stays, so the remote refuses the push. So the harness never overwrites a commit that someone else pushed to `<n>`, even after a fetch moved the remote-tracking ref: the remote refuses the push. This push skips the pre-push hooks of the project (`--no-verify`), as the commits of the harness skip theirs, so a hook that rejects work in progress does not stop the backup and other issues do not wait on the hook for the fetch lock. The push is only a backup: when it fails, the harness writes a `branch.push-fail` event and the issue goes on. The harness never pushes a `<n>-dispute-*` branch. When a git hook stops a commit, the agent that made the change gets the hook output, fixes it, and the harness commits again. A `commit:` line in the reply of the agent replaces the subject, so a hook that rejects the subject can pass. The harness drops each GitHub closing keyword (`close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`) that names an issue from the subject, so a push to the base never closes an issue: the issue closes only after its checks pass. Every commit the harness makes has a one-line message with no body: the subject, then the issue number, as in `fix(worker): kill stray processes (#597)`. The harness replaces any `(#N)` suffix at the end of an agent subject with the number of the issue. With no subject from the agent, the subject is `fix: <issue title>`, and a revert has `revert: <issue title>`; the harness drops closing keywords from these too. The budget is `maxCommitFixes`. Any other git failure in the commit stops the run with an error. An implementer that makes no change hands the issue to a person, unless the branch is already ahead of the base, for example when an issue resumes from saved state in phase `claimed`, or when the remote holds branch `<n>`: the run then carries on with the commits on the branch, and the newest of them gives the subject of the landed commit. A lost state file does not count, since an issue with no saved state resets its local branch (step 3). When the base already does all that the issue asks, the implementer makes no change and ends its reply with a `done: <evidence>` line. If the branch is not ahead of the base, a reviewer then checks that claim against the base. The harness puts the branch back after this reviewer as it does after the reviewer of step 5, also when it times out, fails or the run stops. When it raises no blocking finding, the harness comments `### next-issue · Worker: already done` with the evidence and the summary of the reviewer, adds `status:done` and closes the issue as completed, and the issue ends as `done`. The state file keeps that comment from the closing mark until it is posted, so a run that stops before it posts the comment posts it when it closes the issue. Once the comment is posted, the state file says so, and no resume posts it again, also after a hand-over when the label or close fails. Otherwise it hands the issue to a person with the reason `already done disputed`, and the comment holds the evidence and the findings of the reviewer. A reply with a `question:` line asks the questions instead. To close a parent issue once its sub-issues land, mark it as blocked by each sub-issue and give it the `status:todo` label: it waits while a sub-issue is open (step 1), then the implementer finds it already done and the harness closes it. The implementer checks the issue first. When the scope, the expected behaviour or the acceptance criteria are ambiguous, it makes no change and asks instead of guessing, with each question on its own `question: <n>. <question>` line, its options labelled by letters and one option recommended. A reply with at least one `question:` line makes the harness drop any change in the worktree, commit nothing and hand the issue to a person with the reason `questions`. The hand-over comment lists the questions in order, numbered by the harness. The harness reads the issue again and adds the questions after any text under its `Open questions` heading, or adds that heading at the end of the body when it has none. When that read or body edit fails, the harness records a `questions.body-failed` event in the run log and still hands the issue over with the questions in the comment. When a person without write access last changed the body, the harness leaves the body as it is, records a `questions.body-untrusted` event and does the same (see [Safety](#safety)). It also keeps the questions in the state of the issue, so the implementer of the run that resumes the issue finds them, inside an `untrusted` fence, next to the answer of a person, not in the issue body.
5. Let the reviewer agent judge the diff, at most `diffMaxChars` of it. The reviewer reads files and runs commands in the worktree, so it can prove a finding with the tests or the type check. The harness then throws away every change that the reviewer left in the worktree, so no such change can reach a later commit. When the reviewer left another branch or a detached `HEAD` checked out, the harness checks out the issue branch again at its commit from before the review. It does the same when the reviewer times out or fails. The state file keeps that commit while the reviewer runs, so when the run stops during the review, the next run that resumes the issue first puts the issue branch back at that commit, before the setup command, and the diff it reads holds no reviewer commit. A commit that a person adds to the branch after a hand-over stays on it. The first reviewer also gets the reply of the implementer, and raises a finding when a behaviour change has no failing run of its test. A later reviewer gets the reply of the last review fixer instead, who quotes the failing run of a test for a behaviour change. The harness keeps both replies in the state file, also after a hand-over, so the first reviewer after a resume also gets the reply of the last review fixer when there is one, and the reply of the implementer otherwise. The reviewer ends its last message with its verdict as a json block: a summary and one entry per finding, each rated `blocking` or `minor`. A reply without a valid block hands the issue to a person. The findings are the only ground truth. The reviewer gives no approve or reject field, because such a field can contradict the findings. The harness puts the result on the issue. A result longer than a GitHub comment (65536 characters) is cut to fit, with a last line that says so.
6. An open finding is any finding, blocking or minor, while a review round is left. In the last round, only a blocking finding stays open: a minor finding there goes on the issue but starts no fix, because a fix in the last round gets no review. Thus `maxReviewRounds` of `1` never fixes a minor finding.
7. No open finding means approval: the change lands on the base branch. Approved changes land one at a time, so the next one waits, without a slot, until the checks of the last one end, and other issues go on meanwhile. The harness fetches the remote base, merges it into the branch and makes the change one commit on top of it, with the subject of the implementer's commit. A review fix keeps that subject, but a commit fix for the implementer's commit replaces it, and a fix for failed checks after the landing lands under the fixer's own subject. The reapply commit after a revert uses the subject of the change.

   When git merges the base cleanly, no agent runs. When a conflicted file holds no conflict marker, for example a file that one side deletes and the other changes, a renamed file or a binary file that both sides change, no agent runs: the harness undoes the merge and hands the issue to a person with the reason `merge conflict`, since git leaves only one side in the file. When git reports conflicted files, the fixer gets the list from the check budget, `maxCiFixes`, removes the conflict markers, and the harness commits the merge. A merge that the fixer commits itself counts only when the branch then holds the base commit that was merged and the listed files hold no conflict marker. With the budget used up, or when the fixer leaves a conflict marker or the merge unresolved, aborts the merge, or fails, the harness undoes the merge and hands the issue to a person with the reason `merge conflict`.

   The harness then runs the local gate (see [Local checks](#local-checks)). First it runs the setup command again in the worktree, so the checks use the dependencies of the merged base. It runs the setup after it makes the change one commit, and commits what the setup writes, unless git ignores it, on top of that commit without hooks. Every check runs on that setup commit. After the checks, the harness puts the branch back at the change commit, so what this setup writes does not land on the base; after a stop or kill during the checks, the next run puts the branch back first. What the first setup writes, before the implementer, is part of the implementer's commit and lands. When this setup rewrites such a file, for example a lock file, the checks run on the rewritten file, but the base gets the file of the change. A change that the base already holds is an `empty change` before the setup runs. A setup that fails or does not finish in `setupTimeoutMinutes` keeps the merged commit, stops the landing before the push and hands the issue to a person with the reason `setup failed` or `setup timeout`.

   The harness then runs the `format`, `lint`, `typecheck` and `test` scripts in the worktree, in that order, with `bash -c` and stderr merged into stdout, each for at most `checksTimeoutMinutes`. Their output goes to the run log (`check.output`, and `check.fail` for a failure). After each command, the harness resets the worktree to the commit it checked and removes untracked files that git does not ignore, so a file that a command writes never lands on the base. A command that fails or does not finish stops the landing before the push: the fixer gets the command and the tail of its output (at most `logMaxChars`) from the check budget, `maxCiFixes`, and its fix is squashed into the change, which keeps its subject. The harness then merges the base again and runs every command again, so nothing lands until all pass. When the budget runs out, the harness hands the issue to a person with the reason `local checks failed: <command>`, such as `local checks failed: npm run lint`, and the tail of the output in the comment; a fixer that adds no commit or calls the failure unrelated hands it over too, as for the checks on the base. Nothing of the change reaches the base. A run that stops while a command runs keeps the budget, and the next run merges and runs every command again before any push. The state file keeps the merged commit from the squash until the push, so the next run that resumes the issue first puts the issue branch back at that commit, before the setup command.

   A commit that a person adds to the branch after a hand-over stays on it. When the issue landed a commit before the hand-over, the resume first waits for the checks of that landed commit. When they pass, the harness drops that commit from the landed list and the person's commit lands as a new change, so a later revert takes back only the person's commit and its fixes. When they fail, the fixer runs as usual with the person's commit in place. So a later failure does not revert a landed commit whose checks nobody saw fail.

   The harness then pushes the commit to the base branch, without force. The push runs the pre-push hooks of the project, as does the push of a revert. The harness holds its fetch lock during the push, so while a pre-push hook runs, other issues wait to fetch or to update the base, for up to `commandTimeoutMinutes`. When the push fails, the harness fetches the base first, and treats the push as landed when the base holds the commit, for example after a timeout. When the base moved, for example because someone else pushed first, the harness starts the rebase again, three times at most. When the base did not move, for example on a missing permission or a branch protection rule, the harness hands the issue to a person at once with the reason `push failed`, without running the checks again. Each `push failed` comment holds the tail of the last error of git. When that fetch fails too, the harness hands the issue to a person with the reason `push unknown` and halts, even when the hand-over fails. The state file holds the commit during the push, so a run stopped meanwhile, or the resume after that hand-over (once a person answers or takes the label off), checks the base and waits for the checks of the commit when it landed. Until then, no run lands another change (see below). Once the commit lands, the harness fetches the remote and fast-forwards the local base branch to it when that is safe. A fetch that fails or a fast-forward that is not safe leaves the local base branch as it is and writes a `base.behind` event, and the landing goes on.

   The harness then waits for the checks of the pushed commit on the base branch: the GitHub Actions workflow runs that a `push` of the base branch started on it, its commit statuses and the check runs of every other GitHub App, so checks from another CI service count too. It leaves out the check runs of the GitHub Actions app, since it judges GitHub Actions by its workflow runs. It leaves out workflow runs that any other event (such as `issues`, `issue_comment` or `schedule`) started, since GitHub gives such a run the tip of the default branch as its commit. It also leaves out the `push` runs that a push of a tag or of another branch started on the same commit, such as a release or a deploy. It leaves out every GitHub Actions job, check run and commit status whose name is in `ignoredChecks`: it does not wait for it, its result does not fail the checks and its logs do not go to the fixer. With `ignoredChecks` set, the harness judges each workflow run by its other jobs, so a run whose only failed job is ignored passes when every other job passes. A run that GitHub concludes `success` passes as it is, so a failed job with `continue-on-error: true` does not fail the checks. When an ignored job fails and GitHub cancels another job of the same run, for example through the default `strategy.fail-fast` of a matrix, that job never finished: the harness hands the issue to a person with the reason `main checks cut short` and halts, and the issue stays open. Set `fail-fast: false` on a matrix with an ignored job to avoid this. The same goes when an ignored job fails and another job of the same run ends `skipped`, for example because it `needs` the ignored job; a skipped job in a run with no failed job still passes.

   A failed or errored commit status, or a workflow run or check run that ends with `failure`, `timed_out`, `startup_failure` or `action_required`, fails the checks. The harness does not rerun a workflow run that ends `action_required`, since it waits for a person to approve it. When any check ends `cancelled`, for example because a later push cancelled the workflow run, that check never finished, even when another check (such as a release workflow) ends `success`: the harness hands the issue to a person with the reason `main checks cancelled` and halts, and the issue stays open.

   A repository that reports no check keeps asking for `checkGraceSeconds`. When every check passes, the harness keeps asking until `checkGraceSeconds` have gone by since it first read the checks, since GitHub can add a check a few seconds after the others; a check that shows up in that time counts, and one that shows up later does not. A pending state waits again, up to `checkTimeoutMinutes`. A read that fails is tried again at the next interval. A read that GitHub refuses with a rate limit is tried again after a minute, as often as needed until `checkTimeoutMinutes` runs out; the harness then hands the issue to a person with the reason `main checks timeout` and halts, and the comment says that a rate limit kept the checks from being read. When any 3 other reads of the checks of a landed change fail in a row, for example on an expired token, the harness hands the issue to a person with the reason `checks error` and halts, before the next change lands. The comment holds the error and says that the landed commit is on the base and its checks were not awaited. The state file keeps the commit, so the resume after a person answers or takes the label off waits for its checks, and until then no run lands another change (see below).

   When the checks pass, the harness marks the state file as closing, sets `status:done` and closes the issue. When a run stops or dies before the close, the next run sees the mark, sets `status:done` and closes the issue, with no new push, revert or hand-over. A hand-over clears the mark, so an issue taken back after a failed label edit or close is resumed, not closed, by later runs. When a run stops or dies after the close, before the state file goes away, the next run finds the closed issue through its state file and removes the worktree, the local branches, the remote `<n>` branch and the state file, with no new push to the base, revert, label, close or hand-over. A label or close that fails for another reason hands the issue over, and it then waits for a person like any other hand-over. Then the worktree, the local branch, the remote `<n>` branch and the state file go away. A hand-over or a failure keeps the remote branch. The harness deletes the remote branch only while it is still at the commit the harness last pushed, so a commit that someone else pushed to `<n>` stays. A remote branch that cannot be deleted stays, and the harness writes a `branch.remote-kept` event.

   When the checks fail, the harness reruns the failed jobs of each failed GitHub Actions workflow run once with `gh run rerun <id> --failed`, records a `ci-checks.rerun` event and waits again once the runs restart. A failed run whose failed jobs were already rerun (its attempt on GitHub is above 1) is not rerun again, so a resumed run reruns only the runs not rerun yet. A failure that gets a rerun ends the wait at once; any other failure (a run that was rerun, a run that waits for approval, a check from another CI service) waits until every check has finished, so a workflow run that fails later, even after the first rerun started, still gets its own rerun before any fixer. A workflow run whose kept job failed while a job in `ignoredChecks` still runs gets its rerun only once the whole run has finished on GitHub, as GitHub refuses to rerun a running run. A rerun that GitHub refuses because the run is already running counts as started. When at least one run restarted and a later rerun or read fails, the event carries the error and the harness still waits for the checks again, counting each restarted run as running until a later attempt of it completes, so the fixer never runs while a rerun is queued or in progress.

   When the rerun cannot start (no run restarted, a `ci-checks.rerun-failed` event), or the checks fail again with no run left to rerun, the fixer gets their logs from the check budget (for a check from another CI service, only its name and link), and its fix lands the same way. When the fixer cannot fix them, its fix cannot land, an error stops the fix, or the budget runs out, the harness reverts every commit of the change on the base branch, pushes the revert and hands the issue to a person. When the base already holds a revert of those commits, for example one that a person pushed, the harness pushes no revert, says that the change is already reverted, puts the change back on the branch on top of the base, as after a revert, and hands the issue to a person. When the push of the fix ends as `push unknown`, the harness does not revert: it hands the issue over and halts as for any other `push unknown`. A revert push that the remote refuses, for example because the base moved, makes the revert again on the new base, three times at most. A failed revert push that the base holds after a fetch counts as landed. Once the revert lands, the harness fast-forwards the local base branch to it, as after a landed commit. When that fetch fails too, the revert may be on the base with checks nobody awaited: the harness reports it so, saves the halt and blocks later landings. The state file holds the revert commit during the push, so a run stopped meanwhile checks the base on resume. When the base holds the revert, the harness puts the change back on the branch on top of the revert, as after a revert that completes (an unlanded fix commit is dropped), drops the landed commits from the state, waits for no checks, does not revert again, hands the issue to a person with the reason `revert stopped` and halts.

   A resume that stopped while the checks of a landed commit ran waits for them again, even when more commits landed on the base since, and a fix that was committed but not landed lands first. Before that, the resume drops any change left in the worktree, including a merge of the base that a stopped fix landing left in progress, so the fix merges the current base again from the start.

   A problem that the reviewer leaves out of the findings thus gets an approval: only the findings count.

8. With an open finding, run the fixer agent and go to step 5 again. The budget is `maxReviewRounds`. A fixer that holds every finding to be wrong changes nothing and gives its reason instead. The reason goes on the issue and into the next round, where it answers every finding of its own round, so the reviewer withdraws them all or repeats them all. With only some findings wrong, the fixer fixes the correct ones, and the next round holds the rest. A fixer that settles every finding with no code change, for example by showing a failing test run, changes nothing and ends with a `resolved:` line instead. The note goes on the issue and into the next round in the same way, and a change it leaves behind is handled as for a dispute.

## Issue format

Every agent prompt holds the body of the issue and the comments of users with write or admin access to the repository. An issue reads best with these sections, in this order:

1. `Problem`
2. `Context and findings`
3. `Decisions`, empty when no choice needed asking
4. `Acceptance criteria`
5. `Out of scope`
6. `Open questions`, empty when the issue is created

The list lives in `src/shared/issue-format.mts`. The [`create-issue` skill](#create-an-issue) writes an issue in this format. The harness does not reject an issue without the format.

## Rules for the agents

The implementer and the fixer get these rules in their prompt, and the first reviewer checks them:

- update the documentation for a change of behaviour or a feature that is added or removed;
- remove the tests of a feature or behaviour that is removed;
- test behaviour that a user can observe, and give each test a description that names the actor, the action and the observable outcome;
- write no test when there is no behaviour to test, such as a change to docs, config or other text;
- reuse existing code and patterns, stay consistent with the repository and pick the simpler option;
- check an API, a command or a url in the repository or its dependencies before using it, and invent none;
- keep each README to what a user needs to start and use the tool, and put edge cases and internal behaviour in other docs.

The reviewer rates a missing documentation update or a test that is not observable as a finding. In every round, it gives the file and line, or the command output, that supports each finding. Personal style rules, such as spelling, code comments or binding names, belong in the `CLAUDE.md` of each repository.

## Stops for a loop

The harness hands the issue to a person, with the `status:needs-human` label, and comments the reason on the issue, when:

- the check budget or the review budget runs out. A finding that the reviewer repeats, even one that the fixer disputed or settled, goes back to the fixer until the review budget runs out;
- a fixer round adds no commit and gives no reason, so there is no progress;
- the fixer reports that the checks fail for a reason the change did not cause, such as a test already broken on the base branch or one that fails only under load. It changes nothing and the reason reaches the issue, rather than the fixer spending its whole budget on a failure it cannot fix. The revert of the change reuses the worktree, so a change the fixer leaves behind does not stay there: its edits are committed with no hooks on top of any commit of its own, that commit moves to a new local `<n>-dispute-<commit>` branch, the worktree goes back to the `<n>` branch (also when the fixer switched to another branch), and the hand-over comment names that branch. The branch goes away with the `<n>` branch when the issue is done. For the checks on the base, a failure in a file that the change added or changed is never unrelated: when the failed logs name such a file (by its path, or by a tail of its path that keeps a folder, with no folder before either, so `packages/a/src/index.ts` does not name `packages/b/src/index.ts` and `node_modules/x/package.json` does not name `package.json`; only `./` or the GitHub Actions checkout folder `<repo>/<repo>/`, with the repository name in any case, may come before the whole path), the harness refuses the claim and gives the fixer another round from `maxCiFixes`, with a note that names the file. A later hand-over comment of the same run, such as for a fix that fails its checks too or fails to land, still names the dispute branch of each refused round;
- a fixer disputes or settles the findings and leaves a change behind, either in the worktree or in a commit of its own. A dispute carries a reason, not a diff, and a retry of the issue cleans the worktree before the next review, so the change does not stay there: its edits are committed with no hooks on top of any commit of its own, that commit moves to a new local `<n>-dispute-<commit>` branch, the worktree goes back to the `<n>` branch (also when the fixer switched to another branch), and the hand-over comment names that branch. The `<n>` branch keeps only what will land, and the reviewer of a retry sees none of the change. Neither lands. The `<n>-dispute-<commit>` branches go away with the `<n>` branch when the issue is done;
- the reviewer gives no verdict, or the checks do not finish in time;
- a script of the local gate still fails before the push when the check budget runs out; nothing of the change is pushed;
- the push to the base branch fails while the base did not move, or fails three times;
- the checks on the base branch fail and the fixer cannot fix them, an error stops the fix, or they do not finish in time. The base branch is then broken, so the run claims no new issue and ends once the running issues end. It halts this way even when the hand-over fails; the issue then ends in error with both the reason and the hand-over error;
- the implementer asks questions about the issue (reason `questions`);
- a person without write access last changed the title or body of the issue (reason `untrusted editor`, see [Safety](#safety)). On a resume whose state holds a landed commit, or a push or revert that may have reached the base, this check runs before the harness checks the base, so it then also halts the run, as a failed setup does;
- an agent does not finish in `agentTimeoutMinutes`;
- the setup command fails, or does not finish in `setupTimeoutMinutes`. On a resume whose state holds a landed commit, or a push or revert that may have reached the base, the setup runs before the harness checks the base, so it then also halts the run, with the commits and state kept for the next run. The comment says what may be on the base and that its checks were not awaited;
- a step of the run fails with an error. A `gh` call that is safe to repeat, such as a read or a label edit, is tried up to three times first when the network fails or GitHub answers `Something went wrong while executing your query`. So is a `gh run rerun`: when GitHub took the first try, it refuses the next as already running, which counts as a started rerun. A `gh issue comment` is tried once, so a lost reply never makes a duplicate. A label edit adds the new status label before it removes the old ones in a second call, so a failed edit leaves the old status label on the issue. On a resume whose state holds a landed commit, or a push or revert that may have reached the base, an error before the harness checks the base (for example a failed fetch of the base, or a worktree that cannot be made) also halts the run, as `push unknown` does. The issue ends in error, the comment says what may be on the base and that its checks were not awaited, and the state keeps the commits for the next run.

After a halt, a running issue that reaches the landing does not land on the broken base branch: it ends `stopped` with the reason `run halted` and keeps its state, branch and labels. The next run resumes it and lands it with no new review.

A halt that leaves a commit on the base, or a push or revert that may be on it, with checks nobody awaited (`checks error`, `push unknown`, `main checks timeout`, `main checks cancelled`, `main checks cut short`, an error, a failed setup or an `untrusted editor` hand-over on such a resume before the base is checked, or a stop or kill while the run pushes a change to the base, waits for the checks of a commit it landed, or fixes the failed checks of that commit before the fix lands or the revert of that commit ends) is saved in the state file of its issue. A stopped issue resumes in the next run; any other waits for a person, so later runs skip it. Either way, no later run lands another change meanwhile: an issue that reaches the landing ends `stopped` with the reason `base unchecked`, keeps its state, branch and labels, and the run claims no more issues; the log holds a `land.blocked` event with the waiting issues. Runs take such a halted issue before the others, and a running one still resumes, so an older issue that reaches the landing first does not keep it from checking the base. Once a person answers or takes the label off, the issue resumes, checks the base and waits for the checks of its commit; when those are known (the issue is done, or its commits are reverted or found not on the base), the issue drops the halt from its state and the next run lands the held issues again. A later landing of that issue blocks other runs only if it halts again. A person who gives such an issue up instead (the `skip` label, which **Give up** in the `answer-hand-over` skill adds) releases the block, but only when the last person to add the `skip` label has write access to the repository: the next run skips the issue, drops its halt from the state and logs a `land.released` event, so other issues land again on a base whose last checks nobody read. A `skip` label added by anyone else keeps the block: the run skips the issue and keeps its halt. The state keeps the commits, so taking the `skip` label off later resumes the issue and checks them. Such a resume is not held back by another halted issue while it only checks its commit already on the base; a fix it has to land waits like any other change. The hand-over comment says so. A halted issue that was deleted or moved to another repository can no longer be answered or given up, so the next run that gets a not-found error when it reads the issue releases it the same way: it drops the halt from the state, keeps the commits and logs a `land.released` event with the reason `issue not found`. Any other read error (for example a network error) keeps the block for that run. A person who closes such an issue releases the block too: the next run logs a `land.released` event with the reason `closed`, then drops the state of the issue, halt included, so other issues land again on a base whose last checks nobody read.

The fixer sees the findings of all earlier rounds, not only the last one, with its own disputes next to them. From round two, the reviewer judges only the earlier findings and any regression.

Each comment that the worker posts on the issue starts with one heading line of the form `### next-issue · <Agent>: <outcome>`, with the details below it: `### next-issue · Review: approved`, `### next-issue · Review: changes requested`, `### next-issue · Fixer: no change`, `### next-issue · Fixer: settled with no change`, `### next-issue · Worker: already done` and `### next-issue · Hand-over: needs help`. The account is the same for all of them, so the heading, not the author, tells them apart. A comment longer than 65536 characters is cut to fit and ends with the line "This comment was too long for GitHub and was cut." The agents get no comment that starts with `### next-issue ·`, so a comment of an agent never returns to a prompt: the dispute of the fixer reaches the reviewer through the state file. The one exception is the answer to a hand-over, see [Retry an issue that waits for a person](#retry-an-issue-that-waits-for-a-person).

## Stop a run

Run `npx -y next-issue@latest stop` to stop a run, see [Worker](#worker). The run claims no new issue, the harness finishes every issue that it holds and then writes the summary as usual. `npx -y next-issue@latest start` does not stop a run: it exits as soon as the run has started.

A client of the worker can stop a run sooner with the `after` of its `stop` message:

1. `round` stops every running issue after its current round: the implementation or one review round (review, then fix). An issue that lands goes on until its checks on the base branch end. The issue ends as `stopped`. Its state, worktree and labels stay, so the next run carries on from that point.
2. `now` kills every agent at once with `SIGKILL` to its process group and sends `SIGINT` to the process group of each running command, so each running issue stops in the middle of a step and ends as `stopped`. The saved state lets the next run continue the issue. Edits that an agent did not commit stay in the worktree. When the issue resumes in review, the harness drops them before the reviewer starts, so the reviewer sees only the commits of the branch. Files that git ignores, such as build output, stay. When it resumes before the first commit, the implementer runs again and the commit holds them. A review round, a check fix or a commit fix whose reviewer, verdict comment, fixer, commit fix agent or read of the failed logs this stop kills does not count, so the next run runs that step again with the same budget. A rerun of the failed jobs on the base branch that this stop kills before any job restarted runs again in the next run, before any fixer. A command that is still running 10 seconds after the `SIGINT` gets `SIGTERM` to its process group, and 10 seconds after that `SIGKILL`, so a command that ignores `SIGINT` holds the stop for about 20 seconds at most. A command that exits on `SIGINT` gets neither.

`SIGTERM`, `SIGHUP` or `SIGINT` to the worker act like `now`: they stop the running harness commands and agents, with the commands the agents started, and give back the review round, the check fix, the commit fix and the rerun in the same way. A command that ignores the signal gets `SIGTERM` and then `SIGKILL` on the same timings, and the worker exits once its commands end, so about 20 seconds after the signal. A command that has not ended 10 seconds after the `SIGKILL` holds the worker no longer, so it exits about 30 seconds after the signal at most. Meanwhile the running issues start no new command or agent, as after `now`. Until it exits, the worker refuses `start` and `stop` with `the worker is stopping`, which the command prints on stderr with exit code 1.

When the worker crashes on an uncaught error or an unhandled promise rejection, it writes a `worker.exit` record with `reason=crash` and the stack to its log (see [Worker](#worker)), kills the process group of every running agent and command at once with `SIGKILL`, removes its lock and socket files and exits with code 1, so no agent edits a worktree once the worker is gone. The saved state lets the next run continue each issue. A `kill -9`, an out-of-memory kill or a native crash of the worker leaves its agents and commands running.

When the reviewer approved the change and the run stopped before its commit reached the base branch, the next run drops those edits and any unfinished merge of the base branch, then lands the change with no new review round. A hand-over of the issue cancels that approval, so the issue resumes in review. A revert of the landed change cancels it too, even when the hand-over after it does not finish.

The agents run inside the harness, and their commands and the harness commands run in a process group of their own, so a signal to the harness does not reach them directly. When a command that the harness runs, such as a setup command or a script of the local gate, exits, the harness kills its process group with `SIGKILL`, so a background process that it leaves behind ends too, including a daemon such as the Gradle daemon. A process that leaves the group, for example with `setsid`, keeps running.

The harness runs all git and `gh` commands itself. The commit holds all the changes in the worktree, so a setup command that writes a file that git does not ignore puts that file in the commit. The reviewer is the one agent whose changes never get that far: the harness discards them, undoes any commit that the reviewer made on the issue branch and checks that branch out again, before it reads the verdict.

## Safety

Every agent can run a shell command. The implementer and the fixer run with the permission checks off; the reviewer runs with a smaller tool set, but its shell has no limit on the commands. They all start in the worktree, but nothing holds them there: they can run any command, with your rights, anywhere on the machine. The prompt holds the title and the body of the issue, which come from GitHub. It also holds the comments of the issue, but only those by users with write or admin access to the repository. The harness leaves out every other comment and writes a `comment.skip` event with its author to the run log. If an access check fails for a reason other than a 404, the issue stops with an error.

After the setup, and before any agent runs, the harness finds the last person to change the body (the author when nobody edited it) and the last person to change the title (the author when nobody renamed it). When either has no write or admin access, no agent gets the issue: the harness hands it to a person with the reason `untrusted editor`, and the comment names each such person. The agent gets the title and body read in the same query as their editors, so an edit made after the harness listed the issue is never sent unchecked. A writer who checks the text and then changes the named title or body makes the issue go on after the answer. This matters most on a public repository: anyone can open an issue there, and its author can edit the body after a maintainer adds the ready label, before the harness claims it. An issue opened by a person without write access thus always waits for a writer to change it. When the issue was deleted or moved to another repository before this check, the run fails with the reason `Issue #<n> was not found: it was deleted or moved to another repository.` When the implementer asks questions, the harness writes them into the body only when a writer last changed it; otherwise the body edit would make the harness its last editor and pass the unchecked text. It hands the issue over with the questions in the comment instead, and the run that resumes it after the answer hands it over again with the reason `untrusted editor`.

The prompt puts the body of the issue, check logs, hook output, the diff, the replies of other agents, and the findings, disputes and settled notes of earlier review rounds inside `untrusted` fences, each longer than any backtick run in its text, and tells the agent to treat that text as data, not instructions. The comments of writers, a writer's answer to a hand-over, and the harness's own round labels and dispute and settled lines stay outside the fences.

Thus a writer can still give an instruction to the agent, and the agent can read other text, such as linked issues or files, by itself. Use the harness only on a repository where you trust the writers, or run it in a container.

[ADR 0007](https://github.com/ravshansbox/next-issue/blob/main/docs/adr/0007-agent-isolation.md) records why the agents keep a full shell, and which other options were considered.

No person checks a change before it lands. To replace those checks, the harness always runs the local gate before a push (see [Local checks](#local-checks)), and [ADR 0002](https://github.com/ravshansbox/next-issue/blob/main/docs/adr/0002-humanless-flow.md) recommends a different model for the reviewer than for the implementer and the fixer in `models`, and running the whole harness in a container.

## Observability

Every run has an id, `<timestamp>`, and writes these under `.next-issue/runs/`:

- `<id>.jsonl` — one JSON object per event, with `ts`, `runId`, `kind`, and the `issue`, `role` or `round` in scope. A run with `--watch off` whose fetch of the issues fails ends with an `issues.fail` event; a watching run writes an `issues.unreadable` event instead and goes on (see the watch below). A run that fails in any other way once this file is open, for example when `gh repo view` fails at the start or an issue crashes the run, ends with a `run.fail` event (after `run.end` when the run got that far). Both carry the `error`;
- `<id>.summary.json` — token totals per agent role, event counts, and one report per issue with the outcome, the reason and the budgets used (in a watch run, an issue skipped in several passes gets one report, and an issue handled in more than one pass keeps a report for each; when an issue crashes the run, the file still holds the reports of the issues that finished);
- `<id>/sessions/` — the full Claude Code session of each agent call, one message per line, with every message, tool call and tool result. The session id in a `usage` event is the file name.

At the start of a run, the harness deletes the files and folders under `.next-issue/runs/` that are older than `keepRunDays`. The age of a folder is the time since the last change to it or to anything inside it, so the sessions of a long run stay while it still writes them. Set the field to `0` to keep them all.

The worker also sends the summary to its clients in its `pass` and `end` messages (see [Worker](#worker)). All progress goes to standard error.

Recorded for each step: `claim`, `comments`, `reply`, `worktree`, `setup`, `editors`, `implement`, `review`, `fix`, `commit-fix`, `rebase`, `land`, `ci-checks`, `revert` and `hunt`, each with a `.start`, `.end` or `.error` event and a duration in `ms`. Every `git` and `gh` command is recorded with its exit code and duration. A `tool` event holds the tool name. For a `Bash` tool it holds the command too, and for a `Read`, `Write`, `Edit`, `Grep`, `Glob` or `NotebookEdit` tool the `path` it got, relative to the worktree when inside it. Each agent call adds a `usage` event with the tokens, the turn count, the tool-call count, the model and the session id. A call that times out, ends with a model error or is stopped after its session started adds one too, and its tokens count in the summary totals.

```bash
jq -r 'select(.kind=="usage") | [.issue,.role,.turns,.total] | @tsv' \
  .next-issue/runs/*.jsonl
```

`npx -y next-issue@latest logs` shows the newest run log, one readable line per event, and then prints new events as the run adds them, until `Ctrl-C`. In a terminal it starts with about one screen of the last events, since a long event may wrap onto more than one row; in a pipe it starts with all of them. It stops when the reader of the pipe closes it; on Linux it notices this only at the next event. When the worker restarts and starts a new run log, `logs` prints the rest of the old one, then a line `— new run: <file name> —`, then every event of the new one. This also shows a run of the worker, whose progress goes to no terminal.

The console shows the run and issue milestones, verdicts, hand-overs, errors, each step end, each tool call and failed commands. It leaves out each step start, each command that succeeds, the output of the checks and the agent text; the run log and the sessions hold them. Each line cuts a field at 120 characters, except the `command` of a tool call, which it shows in full. An event of an agent shows its role before its kind, such as `#607 fixer.tool name=Bash command=…`, and a `tool` or `tool.error` event shows the tool as `name`.

## Requirements

- Node 24 or later
- git 2.40 or later (every commit runs `git hook run`, every conflict with the base runs `git check-attr --source`). A run or `serve` run on an older git stops before it claims an issue, with an error that names both versions (in `.next-issue/worker.log` for a run that `start` started).
- `gh`, authenticated with write access to the repository
- a `remote` on GitHub: `github.com`, or a GitHub Enterprise host. Every `gh` call names the host of the remote url (`--repo <host>/<owner>/<name>`, `gh api --hostname <host>`) when it is not `github.com`, so `gh` must be logged in to that host. For an ssh url the harness reads the real host of an ssh alias with `ssh -G`. The host `ssh.github.com` (GitHub's ssh over port 443) means `github.com`. Other hosts, such as GitLab, are not supported.
- Claude Code, logged in, such as with a Pro or Max plan. The harness asks for no API key. The agents run the Claude Code that comes with the Agent SDK, with the model (unless `models` sets one), the settings, the plugins, the skills and the `CLAUDE.md` files of your Claude Code setup, except the `create-issue` and `answer-hand-over` skills, wherever they are installed, since they are for people, not for the agents. So a skill of your own with one of those names does not reach the agents either. The agents run with every permission granted, as no person is there to answer a prompt. The implementer and the fixer get every tool. The reviewer gets every tool except `Write`, `Edit` and `NotebookEdit`. The agents run with `GIT_OPTIONAL_LOCKS=0`, so a `git status` from an agent does not hold the index lock while the harness commits.
- a `package.json` at the root of the base branch on the remote with the scripts `format`, `lint`, `typecheck` and `test`, see [Local checks](#local-checks)

## Local checks

The harness needs no person to check a change before it lands, so it relies on four scripts in the `scripts` of the `package.json` at the root of the base branch on the remote (`<remote>/<base>`): `format`, `lint`, `typecheck` and `test`. Their presence shows that the owner of the project has set up these tools on purpose. It reads only the root `package.json`, not those of workspace packages. Each worktree is cut from `<remote>/<base>`, so the harness fetches the base and reads its `package.json`, not the one in the main worktree: commit and push the scripts before you start. Each script must fail on a problem; `format` must check the formatting and not write files. [ADR 0009](https://github.com/ravshansbox/next-issue/blob/main/docs/adr/0009-fixed-check-scripts.md) records why.

Before each push to the base, the harness runs the setup command again, then `format`, `lint`, `typecheck` and `test`, in that order, in the worktree, each for at most `checksTimeoutMinutes` (see step 7 of [What it does](#what-it-does)). It runs them with the package manager of the lock file in the worktree:

| Lock file                               | Command             |
| --------------------------------------- | ------------------- |
| `pnpm-lock.yaml`                        | `pnpm run <script>` |
| `yarn.lock`                             | `yarn run <script>` |
| `bun.lock`, `bun.lockb`                 | `bun run <script>`  |
| `package-lock.json`, or no JS lock file | `npm run <script>`  |

When the root `package.json` of `<remote>/<base>` is missing or lacks any of the four scripts, `npx -y next-issue@latest start` stops before the run starts, a run (also a resume on an upgraded worker) fails before it claims an issue, and `npx -y next-issue@latest init` writes the config and installs the skills, then exits with 1. Each prints an error that names the base (such as `` `origin/main` ``) and each missing script (all four when there is no `package.json`), asks you to commit and push the scripts, says that the humanless flow relies on these checks instead of a person, and says that `format` must check the formatting, not write files. `start` and `init` find the base as a run does, through `gh` and the `remote` of the config. Each such check fetches the base into a git ref of its own under `refs/next-issue/` and removes that ref after it reads the `package.json`, so two `start` commands, or a `start` and a run, can check the base at the same time. When the fetch of the base fails, `start` stops with the fetch error. When `init` cannot read the base, such as with no remote, an empty remote, a failed fetch or `gh` not logged in, it prints `could not check the scripts on the base branch: <reason>` on stderr and exits with 0.

The worker checks the scripts too, each time a run starts, also when it resumes a run on a newer worker after an upgrade. A run without them claims no issue and fails with the same error, which the status shows and `.next-issue/worker.log` keeps.

## Configuration

To set up a repository, run the `init` command in it:

```bash
npx -y next-issue@latest init
```

The command writes `.next-issue/config.json` in the main worktree and adds `.next-issue/`, `.claude/worktrees/`, `.claude/skills/create-issue/` and `.claude/skills/answer-hand-over/` to `info/exclude` in the git directory, which linked worktrees share. The skills belong to next-issue, so a project copy stays out of `git status`; your own skills in `.claude/skills/` stay visible to git. It removes the `.next-issue/` line that next-issue once wrote to `.gitignore`, and deletes `.gitignore` when nothing else is left in it. It keeps a `.claude/worktrees/` line there, since Claude Code puts its own worktrees in that folder too. It leaves every worktree, folder and file in `.worktrees/` as it is. When you upgrade from an older version of next-issue, which kept its worktrees at `.worktrees/hunt` and `.worktrees/<n>`, remove those that are left by hand with `git worktree remove <path>` (first commit any edits you want to keep), since next-issue now works in `.claude/worktrees/next-issue-<n>`. Until you do, an issue whose saved branch such an old worktree still holds is handed over with a reason that names that worktree, as for any other worktree that holds the branch. It moves a `next-issue.config.json` in the root to `.next-issue/config.json`; every other command stops while that old file is there. When the config file is there already, it keeps it unchanged and prints `kept <path>`; `--force` replaces it with the defaults. When both files are there, `init` changes neither and exits with 1 and the error ``.next-issue/config.json exists already. Use `--force` to replace it.``; `init --force` then replaces `.next-issue/config.json` with the old file, not with the defaults. It also installs the skills, see [Skills](#skills). Any other command with `--force` exits with 1 and the error `` `<command>` does not take `--force`: it belongs to `init` ``. The file holds no `setupCommand`, because the harness deduces one from the lock file of the project.

`start` and `serve` also add the four lines to `info/exclude`, and remove `.next-issue/` from `.gitignore`, so a repository needs no `init` to run. They do not create the config file.

The harness writes its JSON files (the config file, the state files and the run summary) with the keys sorted alphabetically at every level. Each run that `start` or `serve` begins sorts the keys of an existing config file the same way, and sorts `ignoredChecks`; it keeps the fields and values you wrote, and adds no default. It leaves a file that is already sorted, or that stops the run, untouched.

With no file, every field keeps its default. A field that is not in the file keeps its default. A file that cannot be read, a file that is not valid JSON and a field with a value of the wrong type stop the run, so a mistake cannot pass without a word. `init`, `start` and `serve` remove from the file each field that the harness does not know, such as `checks` or `draftPullRequest` from an older version, and each unknown key inside `labels` and `models`, before the run reads the file. They print a line for each, such as `removed checks from .next-issue/config.json`, so a typo in a field name shows there. This removal leaves a file with only known fields as it is. The run itself still reads the file strictly: an unknown entry that reaches the file after this removal, such as one written between `start` and the moment the worker reads the file, stops the run with `holds an unknown field` (or `model role`, `label name`); the next `start` removes it.

The hunter adds `labels.hunt` to each issue it files, so you can tell those issues apart from your own and filter them. It also adds `labels.ready`, so the watch claims those issues with no person adding a label.

The names in `labels.ready`, `inProgress`, `inReview`, `done`, `needsHuman`, `skip` and `hunt` must be distinct, also when case is ignored; two equal names stop the run with an error that names both fields. A label name may not contain a comma (`,`) or a double quote (`"`), since `gh issue edit --add-label` and `--remove-label` read their values as comma-separated lists; such a name stops the run with an error that names the field.

An empty `labels.ready` turns the ready requirement off. The harness then claims every open issue that no other label holds back. A run then writes a `labels.ready.empty` warning to the log at start.

The harness compares the labels on an issue with the configured names without case, as GitHub does, so `Status:Todo` counts as `status:todo`.

The log gives the reason for a skipped issue as `stop-label`, `not-ready`, `in-flight` or `blocked`, the last one with the open blockers.

A role set to `null`, or with no entry in `models`, uses `models.default`. When `models.default` is `null` or missing too, it uses the default model of your Claude Code settings. A model in the old `provider/model` form, such as `anthropic/claude-opus-5-5`, makes the agent fail with an error that asks for a Claude model ID.

Without a `setupCommand`, the harness looks for a lock file in the new worktree, and in the worktree after each merge of the base before the local checks, and runs the install command that goes with it:

| Lock file                              | Command                                                                              |
| -------------------------------------- | ------------------------------------------------------------------------------------ |
| `pnpm-lock.yaml`                       | `pnpm install --frozen-lockfile`                                                     |
| `package-lock.json`                    | `npm ci`                                                                             |
| `yarn.lock`                            | `yarn install --frozen-lockfile`, or `yarn install --immutable` with a `.yarnrc.yml` |
| `bun.lock`, `bun.lockb`                | `bun install --frozen-lockfile`                                                      |
| `Cargo.lock`                           | `cargo fetch --locked`                                                               |
| `go.sum`                               | `go mod download`                                                                    |
| `uv.lock`                              | `uv sync --locked`                                                                   |
| `poetry.lock`                          | `poetry install`                                                                     |
| `Gemfile.lock`                         | `BUNDLE_FROZEN=true bundle install`                                                  |
| no JS lock file, with a `package.json` | `npm install --no-package-lock`                                                      |

The harness takes the first JS lock file in that order (the first five rows) and the first other lock file, and joins their commands with `&&`, JS first, so a project with `package-lock.json` and `poetry.lock` runs `npm ci && poetry install`. A project with a `package.json` and no JS lock file adds `npm install --no-package-lock` last, so a project with `Cargo.lock` runs `cargo fetch --locked && npm install --no-package-lock`, and npm writes no `package-lock.json` that could land. A project with neither runs no setup, and a `setupCommand` in the config file always wins. Thus the agents find a worktree with its dependencies in place, and the reviewer can run the tests. Each command holds to the lock file, so a lock file that does not match the manifest stops the issue rather than changing the lock file. The exception is `go mod download`, which can add missing sums to `go.sum`.

A `setupCommand` that fails, or that does not finish in `setupTimeoutMinutes`, hands the issue to a person. The wait for the checks has its own limit, so `commandTimeoutMinutes` holds for every other `git` and `gh` command. State per issue goes to `.next-issue/<issue>.json`, so a new run continues where the last run stopped. The harness writes a state file to a temporary file in the same folder and renames it over the old one, so a state file is replaced in one step: a run killed or a disk that fills up during a write leaves the earlier state. A state file that is not valid JSON, or that does not hold a valid state, gives the issue an `error` outcome that names the file, rather than a silent skip.

The harness does not flush a state file to disk, so a power cut or a system crash can leave it empty, and the issue then ends in `error` at every run. To recover, delete `.next-issue/<n>.json`, take `status:in-progress`, `status:in-review` and `status:needs-human` off the issue and make sure it holds `status:todo` (when `labels.ready` is not empty). The next run then claims the issue as new and starts from the `<n>` branch on the remote, which the harness pushes after every commit, so the committed work stays. The saved progress is lost: the run starts again with the implementer, with full budgets and no findings or review rounds.

Every agent prompt holds `.next-issue/notes.md` when it exists, so lessons such as test commands, tool quirks and deliberate behaviour carry over from one issue to the next. The implementer and the fixer may add a short note to it, and the prompt asks them to keep only what still holds. The reviewer and the hunter only read it.

Every agent also reads each `CLAUDE.md` that Claude Code finds, such as the one in `~/.claude` and the one in the repository. Their rules, such as code conventions and test style, still apply. But the harness owns the issue, the worktree, the branch, git, the commit, the push and the checks, and the prompt says so: a workflow rule in `CLAUDE.md` about these, such as "push to main" or "watch ci", does not apply to the agent. The hunter still files its issues with `gh issue create`.

## Retry an issue that waits for a person

When the implementer makes no change, the hand-over comment holds its full reply after the note, so its reasons and questions can be answered on the issue. When it asks questions on `question:` lines, the comment lists them instead. Every hand-over comment is cut to fit a GitHub comment, whatever the reason, so a long reply or a long run error does not lose it. The reason goes in the body under the `### next-issue · Hand-over: needs help` heading. A cut comment ends with the line "This comment was too long for GitHub and was cut."

A hand-over marks the state file as handed over once its label and comment reach GitHub. When either fails, or the run stops during it, the state keeps its budgets and findings, and a later hand-over of the issue keeps the first reason. A handed-over issue carries the `status:needs-human` and `status:todo` labels, and the hand-over takes `status:in-progress` and `status:in-review` off. With an empty `labels.ready`, it carries only `status:needs-human`. The ready label lets a run find the issue again even when its state file is lost. To give the issue another try, take the `status:needs-human` label off, or answer the hand-over. The next run that claims the issue puts the budgets and the findings back to zero, clears the mark and keeps the branch and the step that the last run reached, so the work carries on where it stopped. After a revert, the branch holds the change again on top of the revert, so the change goes back to the review. An issue that still has the label is not claimed, unless it has an answer to the hand-over: then the run claims it and takes the label off. A label that a person adds to a stopped issue that is not handed over holds the issue, even when an earlier hand-over has an answer. When the label of a hand-over reaches GitHub but its comment does not, an answer to an earlier hand-over does not count: the issue waits, and the worker lists it, until a person takes the label off or a writer comments after that hand-over. Either way, the next run that claims it counts it as a hand-over: it puts the budgets and the findings back to zero and passes on the comments posted after it. When the label edit itself fails, the next run keeps the budgets and the findings.

To give guidance, answer the hand-over with a comment on the issue. When the run resumes the issue, it reads the comments posted after its last `### next-issue · Hand-over: needs help` comment there. Only comments from users with write access to the repository count, for the hand-over comment too. A comment that starts with one of the headings of the harness never counts as an answer. The implementer and every fixer of that run get them in their prompt, under the heading `Answer of a person to the hand-over`. When the questions of the implementer did not reach the issue body, the implementer also gets them under that heading, before the answer, or alone when no comment answers them. A short reply such as "ready, take it" is enough. With no such comment, the run resumes with no guidance. A watching run picks up a comment-only answer at its next pass, not in the pass that is going. A label change, such as Retry in the `answer-hand-over` skill, gets the issue picked up sooner, at the next read of the open issues.

To drop an issue instead, close it. The next run that finds a saved state for an issue that a person closed removes that state file, the `<n>` branch, the remote `<n>` branch, the `<n>-dispute-*` branches and the worktree of the issue. This holds for an issue that waits for a person and for one that a stop left behind. The run starts no agent and makes no push to the base, revert, label change, close or comment, so a change that already landed stays on the base branch. A worktree or branch that cannot be removed stays, and the run log says so. When the issue never opened its own worktree, such as one refused because a person's worktree holds its branch, the run removes only the state file and leaves that worktree and the branches as they are. This also holds for an issue that GitHub still lists as open but reports as closed right before the claim. When such an issue has no saved state, the run removes nothing, since it never opened a worktree of the issue. The issue shows as `skipped` (`closed`) in the summary. A watching run does not claim an issue again once it ended in `error` in that run, so it leaves such an issue for the next run to clean up.

## Skills

The package ships two skills for Claude Code: `create-issue` writes an issue that the worker can claim, and `answer-hand-over` helps you answer a hand-over. `create-issue` starts the run once it files an issue. `answer-hand-over` runs no next-issue command: a watching run picks up a retried issue at its next read of the open issues. Both skills run any next-issue command as `npx -y next-issue@latest <command>`, never from the `PATH`, a global install or a local build. Both skills read `.next-issue/config.json` of the main worktree (the first `worktree` entry of `git worktree list --porcelain`), also when they run in a linked worktree, so `remote` and `labels` hold there too.

`npx -y next-issue@latest init` installs them, so Claude Code finds them:

- `--scope user` writes them to `~/.claude/skills/`, for every repository;
- `--scope project` writes them to `.claude/skills/` of the main worktree of the repository it runs in, also from a linked worktree. It fails outside a git repository.

In a linked worktree, Claude Code loads the project skills of the main worktree only when the linked worktree has no `.claude/skills/` folder of its own. So in a repository that tracks files in `.claude/skills/`, where every worktree has that folder, project-scope skills do not load in linked worktrees. Use `init --scope user` there.

With no `--scope`, it asks which one in the terminal before it writes anything, and fails with exit code 1 on another answer than `user` or `project` (or `u` or `p`). When stdin closes before an answer, such as on `Ctrl-D`, it prints `stdin closed before an answer` and exits with 1. With no `--scope` and no terminal to ask, such as in a script, it fails with `` `init` needs `--scope user|project` ``, exits with 1 and writes nothing. When the question or the answer fails, the config file and `info/exclude` stay unchanged. Any other command with `--scope` exits with 1 and the error `` `<command>` does not take `--scope`: it belongs to `init` ``. It replaces a `create-issue` or `answer-hand-over` folder there whose `SKILL.md` names `next-issue` in its `description` frontmatter line, so files of an older copy go, and keeps the other skills of the folder. It leaves any other folder with that name as it is, as a skill of your own, and prints `kept <folder>: not a next-issue skill`. It copies each skill to a `.<skill>.new` folder next to it first and swaps it in only when the copy succeeds, so when the copy fails, such as on a full disk, the skill installed before stays in place and `init` exits with 1 and `<error>`. It prints `wrote <folder>` for each skill it writes and exits with 0.

`npx -y next-issue@latest start` keeps the skills up to date before it reaches the worker. For each skill, it compares a hash of every file in the shipped folder with each installed copy, in `~/.claude/skills/` and in `.claude/skills/` of the main worktree, so an added, removed or edited file counts as different. It replaces a copy that differs only when its `SKILL.md` names `next-issue` in its `description` frontmatter line, as every shipped version does. It leaves any other folder with that name as it is, as a skill of your own, prints `kept <folder>: not a next-issue skill` on stderr and counts the skill as installed, so it writes no project copy of it. It replaces a next-issue copy that differs in the same way as `init`, through a `.<skill>.new` folder, and prints `updated <folder>` on stderr; when the copy fails, the old skill stays in place and `start` exits with 1 and `<error>`. When neither folder has the skill, it installs it to `.claude/skills/` of the main worktree and prints `wrote <folder>`. It leaves a matching copy as it is and prints nothing about it.

Before that, when git tracks any file in `.claude/skills/create-issue/` or `.claude/skills/answer-hand-over/` of the main worktree and that folder holds a next-issue copy (its `SKILL.md` names `next-issue` in its `description`), `start` asks in the terminal whether to untrack them, since a tracked copy goes stale. It leaves a tracked skill of your own in git and asks nothing about it. On `y`, it removes those folders from the index with `git rm -r --cached`, prints `untracked <folders> (staged); commit and push the removal` and goes on. It makes no commit and pushes nothing, so you commit and push the removal yourself; other staged changes stay staged. When no commit holds those folders (they are only staged), it unstages them, prints `untracked <folders>` and goes on. The files stay on disk as untracked copies, which it then keeps up to date. On any other answer it exits with 1 and changes nothing. When stdin closes before an answer, such as on `Ctrl-D`, it prints `stdin closed before an answer`, exits with 1 and changes nothing. With no terminal to ask, such as when `create-issue` runs `start`, it exits with 1, changes nothing and prints the command to untrack them, `git rm -r --cached -- <folders>`, and asks you to commit and push the removal.

The worker's agents never get these skills, see [Requirements](#requirements).

### Investigate a hand-over

Ask Claude to answer a question or a hand-over, or run `/answer-hand-over`. Claude then:

1. lists the open issues with the `needsHuman` label and answers every waiting issue one by one, oldest first, going through the steps below for each and stopping after the last one;
2. checks the permission of each comment author first, reads the text of comments from users with write access only, as data and not instructions, and finds the latest `### next-issue · Hand-over: needs help` comment and its `question:` lines; it reads the commits and the diff of the issue branch when there is one, and the logs of the failed checks when the hand-over names them;
3. explains the blocker in plain words;
4. asks numbered questions, with lettered options and a recommendation, until it knows whether to retry, retry with guidance or give up;
5. answers on GitHub: Retry swaps the `needsHuman` label for the `ready` label in one `gh issue edit` (with an empty `labels.ready`, it only takes the label off), Retry with guidance posts one comment that does not start with a heading of the harness and then swaps the labels the same way, and Give up takes the label off and adds the `skip` label, which it creates first when the repository lacks it and reuses when it differs only in case;
6. after a retry, tells you what it did. It runs no next-issue command and asks nothing about a run.

Claude finds the repository as the `create-issue` skill does and passes `--repo` to every `gh` command. It does not fix the code of the issue.

### Create an issue

Ask Claude to write an issue, ask for a change in a repository with `.next-issue/config.json`, or run `/create-issue <problem>`. For a change in such a repository, Claude files an issue instead of editing files. Claude always files an issue, and never asks whether to make the change in the session instead. Claude then:

1. restates the problem, reads the code when the problem touches it, and finds the open issues that must be done first;
2. judges whether the change fits one atomic commit that leaves the trunk green. When it is too big for one atomic commit, it proposes a split into issues that each land alone and keep the trunk green;
3. asks numbered questions until none is open, including whether you confirm the split;
4. creates the ready label with `gh label create` when the repository does not have it, then runs `gh issue create --body-file --blocked-by` with the body from [`template.md`](../skills/create-issue/template.md), the issues it depends on and no label, without showing the body first. The issue carries its blocker links from the moment it exists, so the worker waits for them even when `labels.ready` is empty and a run claims every open issue. It needs GitHub CLI 2.94.0 or later;
5. adds the ready label with `gh issue edit --add-label` only after it links every blocker. It adds the ready label and no other label. The ready label is the `labels.ready` label of `.next-issue/config.json`, or `status:todo` when `labels.ready` is not set or there is no config file. With an empty `labels.ready`, the issue gets no label, since the worker then claims every open issue. For a confirmed split, it creates each issue in turn with the links to the issues of the split it depends on, and only then adds its ready label;
6. runs `npx -y next-issue@latest start` once for the issue or a whole split, after the last ready label, also when `labels.ready` is empty. When the run is stopping, `start` fails with `the run is stopping`, so the issue waits for the next run, and the skill does not retry it;
7. gives you the issue url, or each url of a split, and the outcome of `start`, such as `the run is stopping`, in one line, and stops;
8. changes the issue with `gh issue edit --body-file` or `--title` when you ask for a change.

Claude files the issue, the ready label and the blocker links in the repository of the `remote` of `.next-issue/config.json`, or of `origin` when there is no config file or no `remote` field, as the worker does. It passes `--repo` to every `gh` command, so another remote, such as the `upstream` of a fork, never gets the issue.

The issue gets the ready label as soon as its blockers are linked, so a run that is already going may claim it before you review it.

Claude does not implement the issue in that session. The worker does the work. The body holds the sections of the [issue format](#issue-format).

## Commands and options

| Argument                | Effect                                                                                                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `start`                 | Start a run: claim issues, fix them and push them to the base branch                                                                       |
| `watch on\|off`         | Switch watching of the going run, see [Watch for new issues](#watch-for-new-issues)                                                        |
| `hunt on\|off`          | Switch hunting of the going run, see [Hunt for bugs](#hunt-for-bugs)                                                                       |
| `init`                  | Write the config file with the defaults and install the skills, see [Configuration](#configuration) and [Skills](#skills)                  |
| `stop`                  | Stop the going run after its current issues, see [Worker](#worker)                                                                         |
| `status`                | Show the going run, its worker and its running issues, see [Worker](#worker)                                                               |
| `logs`                  | Show the latest run log and follow it, see [Observability](#observability)                                                                 |
| `--scope user\|project` | With `init`: install the skills in `~/.claude/skills/` (`user`) or in `.claude/skills/` of the main worktree (`project`)                   |
| `--force`               | Replace an existing config file, with `init`                                                                                               |
| `--watch on\|off`       | With `start`: on reads the open issues again after each pass, off does one pass and ends. On by default                                    |
| `--hunt on\|off`        | With `start`: hunt the repository for bugs alongside the issues, see [Hunt for bugs](#hunt-for-bugs). Off by default. On needs watching on |
| `--help`                | Show the option list                                                                                                                       |

`--watch` and `--hunt` belong to `start`, and any other command refuses them. Each takes `on` or `off`: with no value or another value, `start` fails with `` `--watch` takes `on` or `off` `` (or `--hunt`) and exits with 1. `--hunt on` with `--watch off` fails with ``hunting needs watching: `--hunt on` does not go with `--watch off` `` and exits with 1. `npx -y next-issue@latest` with no command prints the option list on standard error, starts nothing and exits with 1.

`npx -y next-issue@latest watch on|off` and `npx -y next-issue@latest hunt on|off` switch the run that is going in the worker of this repository, with no restart. They print the new settings, such as `watching on, hunting off`, and exit with 0. `watch off` also turns hunting off, and `hunt on` also turns watching on. When no worker or no run is going, they print `no run is going in this repository`, change nothing, start no worker and exit with 0. With no value or another value, they fail with `` `watch` takes `on` or `off` `` (or `hunt`) and exit with 1. When the worker is older than the command, they fail and exit with 1, since an older worker may not answer; stop the run and start it again. When the worker does not answer within 5 seconds, they fail with `the next-issue worker did not answer` and exit with 1.

The exit code of `npx -y next-issue@latest start` says only whether the worker accepted the run, not the result of the run. The result is in `.next-issue/runs/<id>.summary.json` once the run ends, and in the `code` of the `end` message of the worker: 1 when an issue needs a person or failed, and 0 when it does not.

Version 17.0.0 moved the hunt instructions: the hunter reads `.next-issue/hunt.md` and ignores `next-issue.hunt.md` in the repository root, so a hunter with only the old file gets the built-in prompt. Move the file to `.next-issue/hunt.md`.

Version 12.0.0 made watching the default: `npx -y next-issue@latest start` watches, and `npx -y next-issue@latest start --watch off` does one pass and ends, as `npx -y next-issue@latest start` did before. `--watch` and `--hunt` now take `on` or `off`, so `--watch` or `--hunt` with no value fails and exits with 1: use `--watch on` and `--hunt on`.

Version 11.0.0 dropped `--max <n>`, `--reset`, `--json`, `--verbose` and `--quiet`. `npx -y next-issue@latest start` with any of them, and `npx -y next-issue@latest logs --json`, fail with ``Unknown argument: `<flag>` `` and exit with 1. Instead:

- for `--max <n>`, take the ready label off the issues that the run should leave, or stop the run with `npx -y next-issue@latest stop`;
- for `--reset`, there is no direct replacement: a handed-over issue still resumes with its budgets and findings at zero once a person answers it or takes the needs-human label off, and closing an issue drops its saved state;
- for `start --json`, read `.next-issue/runs/<id>.summary.json`; for `logs --json`, read `.next-issue/runs/<id>.jsonl`;
- for `--verbose`, read the run log and the sessions under `.next-issue/runs/`; for `--quiet`, filter the output, for example with `grep`.

Versions before 7.0.0 started a run with no command, as `next-issue` or `next-issue --once`. From 7.0.0 a run needs `npx -y next-issue@latest start`, and the old form starts nothing and exits with 1. Later versions dropped `--once`: `npx -y next-issue@latest start --once` fails with ``Unknown argument: `--once` `` and exits with 1, so use `npx -y next-issue@latest start --watch off`, which does one pass and ends.

## Watch for new issues

A run with `--watch off` ends when no unseen issue is left. With `npx -y next-issue@latest start`, or `npx -y next-issue@latest start --watch on`, the harness then waits, reads the open issues again and runs another pass, so it picks up an issue that someone opens during the run, or one whose blocker closes. Each pass tries every open issue again, also one that an earlier pass skipped. An issue that failed with an error before the claim is not tried again until the next run. An issue that failed after the claim and was handed over with the needs-human label is tried again once a person answers the hand-over or takes the label off. Within a pass, only a change of labels gets a tried issue claimed again: the harness claims it at the next read when its labels differ from those it had after its attempt, so a hand-over answered with a label change or an unblocked skipped issue does not wait for the next pass. A hand-over answered by a comment alone keeps its labels, so it waits for the next pass. An issue that is done, or that failed with an error and was not handed over, does not come back in the same pass. The hunter counts the same issues as ready.

The waits follow a fixed back-off in minutes: 1, 2, 3, 5, 10, then 10 from then on. A pass that handles an issue, with any outcome other than `skipped`, resets the back-off to 1 minute. A pass where every issue is skipped does not reset it. When a read of the open issues fails, the pass claims nothing more, its running issues go on, and the run writes an `issues.unreadable` event with the `error` to the run log and `.next-issue/worker.log`, then waits with the same back-off and reads again. The run stays `running`, not `failed`. `npx -y next-issue@latest start` on the going run ends a wait at once, so the next pass starts then, and resets the back-off to 1 minute; during a pass it changes nothing about when the run looks next. Each wait writes a `watch.wait` line with the minutes until the next pass to the run log and `.next-issue/worker.log`.

After each pass that handled an issue, the worker sends the summary of that pass to its clients (see [Worker](#worker)). The token totals in it cover that pass only. The summary and the `code` of the run at the end cover all passes.

The watch stops:

- at `npx -y next-issue@latest stop` during a wait, at once;
- at `npx -y next-issue@latest stop` during an issue, after the running issues;
- after a pass that halts the run, for example when the checks on the base branch failed;
- when the open issues cannot be read.

## Hunt for bugs

With `npx -y next-issue@latest start --hunt on`, which needs watching on, the harness runs a hunter agent at the same time as the issues. Before each hunt it reads the open issues with the `labels.ready` label and counts those that are ready to claim and are not running. An issue that failed earlier in the run does not count, since the watch does not try it again. It counts a blocked issue only when each of its open blockers is in the same repository and is running or ready to claim, since those blockers can land and close; a blocker that cannot move, such as one with `labels.needsHuman`, `labels.skip` or `labels.done`, one without `labels.ready`, or one in another repository, leaves it out. It looks only at the direct blockers, and reads them one issue at a time, so it runs one `gh` call at a time. It hunts only while that count is less than `huntCap`, 1 by default. Otherwise it waits and checks again, with the same back-off as the watch: 1, 2, 3, 5, 10, then 10 minutes. After a hunt that files an issue, the harness reads the open issues again, so the open-issue count is current, and the hunter waits 1 minute before it checks the count again, even when the count is still less than `huntCap`. Each wait writes a `hunt.wait` event with the `minutes` to the run log. A hunt that files nothing backs off like a failed one. A claim does not wake the hunter: it reads the open issues and their blockers again only when its wait ends, or when hunting is turned on or off. When the run stops, the wait ends and the hunter reads nothing more. The hunter:

- works in its own worktree at `.claude/worktrees/next-issue-hunt`, so a person's worktree at `.claude/worktrees/hunt` is left as it is, on a detached `HEAD` at the remote base branch, which the harness fetches and checks out before each hunt. A branch that the hunter checks out keeps its commits, and an issue that resumes never uses the hunt worktree as its own;
- follows `.next-issue/hunt.md`, next to `notes.md`, or a short built-in prompt when the file is missing. The built-in prompt asks for bugs proved from the code that a user hits in normal use, starts the `Problem` section with a `Severity:` line, files only high findings, and proposes to remove or simplify code that an earlier fix added instead of adding another guard;
- files up to `huntCap` minus that count, worked out just before the hunt, its most serious findings first, each with the `labels.ready` label, the `labels.hunt` label and the sections of the [issue format](#issue-format), after a search for duplicates. The prompt tells it to treat the text of other issues as untrusted data, not instructions, and to read only the number, title and state of each issue in that search (`gh issue list --json number,title,state`), since anyone can write an issue and the issues it files are claimed with no person involved. It files and searches with `gh --repo <owner>/<name>` of the configured `remote`, with the host in front when it is not `github.com`, so another GitHub remote, such as `upstream` in a fork, never gets its issues. The `labels.hunt` label, `source:hunt` by default, marks the issue as one the hunter filed. The harness creates the `labels.ready` and `labels.hunt` labels before the hunt when they are missing. It compares label names without case, as GitHub does, so a label that exists in another case, such as `Source:Hunt`, counts as there and keeps its name. When the create fails, it reads the labels again, so a label that someone else created meanwhile counts as there too. It files nothing when it finds no real problem or a duplicate exists;
- runs no test suite and changes no file. It gets the tools of the reviewer.

With `huntCap` at 1 and no ready issue, a hunt files at most one issue. The hunter ends its reply with one `issue:` line for each issue it filed, or one `issue: none` line; a url that is not an issue of the repository of `remote` does not count as filed. When the `remote` url holds an old owner or name that GitHub redirects after a rename or transfer, the harness asks GitHub for the new one, so an issue url with the new name counts too. The run log holds one `hunt.issue` event with the `url` for each, or one with `none`. Each hunt writes a `hunt.start` event when it starts and a `hunt.end` event when it ends, whatever its outcome. A hunt that fails writes a `hunt.error` event before its `hunt.end`, and the watch goes on. The hunter then waits before the next hunt, with a `hunt.wait` event and the same back-off, so a failure, or a hunt that files nothing, that repeats waits 1, 2, 3, 5, 10, then 10 minutes, and the back-off goes back to 1 minute after a hunt that files at least one issue. The next pass claims the new issues like any other. At `npx -y next-issue@latest stop` the hunter stops after its current hunt, and the watch ends once the hunt and the running issues end. A `stop` with `after` `now` stops the hunter at once. The hunter stops too when the watch ends for another reason.

In a run of the `serve` worker, a client can switch hunting and watching on or off while the run goes on, with no restart, for example with `npx -y next-issue@latest hunt on` or `npx -y next-issue@latest watch off`, see [Worker](#worker). This works for every run, since `npx -y next-issue@latest start` runs in the worker too.

## Worker

The `serve` command is the internal command that runs the worker of the repository it is run in. `npx -y next-issue@latest start` and worker upgrades launch it, and `start` talks to it, so people do not need to run it. `--help` and the README do not list it. `serve` takes no flags apart from `--help` and refuses any other with an error, because runs start from a client, not from `serve`. Each repository has its own worker, so the runs, restarts and upgrades of one repository never affect another. The worker:

- listens with WebSocket on the socket file `.next-issue/worker.sock` in the repository. Only your user can open the file. It works on macOS and Linux. When the path of the socket file is too long for the system, about 103 bytes on macOS and 107 on Linux, it exits with an error that says so;
- answers a plain HTTP request on the socket file with status 426 (`Upgrade Required`) and nothing else, since it talks WebSocket only;
- holds `.next-issue/worker.lock` in the repository, with its process id and the start time of that process, so only one worker goes per repository. A worker that starts while another process holds the lock exits with `another worker is running`. A lock is stale, and is taken over, when no process has that id or the process with that id started at another time, for example because the system gave the id of a worker that was killed or lost in a reboot to another process. The start time is read in UTC, so it does not depend on `TZ`. When the start time of the process cannot be read, the lock is also held while that process is alive, and stale otherwise. A worker that cannot read its own start time exits with an error and takes no lock. When several workers start at once, one takes the lock and the others exit with `another worker is running`. A worker that stops removes the lock file only while it still holds the lock, and the socket file only while it is still the socket it bound;
- refuses a `start`, `stop`, `watch` or `hunt` message whose `root` is not the exact path of its repository with an `error` message, and starts or stops nothing;
- ignores a message of an unknown type, such as `questions` or `upcoming` from an older client: the client gets no answer;
- sends each `error` as `{ "type": "error", "root": "<path>", "message": "<text>" }`. When a `start`, `stop`, `watch` or `hunt` message carries an `"id"`, the `error` that refuses it carries the same `id`;
- runs at most one run at a time. A client starts it with `{ "type": "start", "root": "<path>", "args": [...] }`. Each run is like `npx -y next-issue@latest start` with those args, or with none when `args` is left out. It takes `--watch on|off` and `--hunt on|off`, and so watches and does not hunt by default, and refuses a command (`start` too), `--force`, `--help` or an unknown argument (such as `--max`, `--reset`, `--json`, `--verbose` or `--quiet`) with an `error` message. A `start` while a run is going (with no `resume`) starts no second run: it switches watching and hunting to the `--watch` and `--hunt` values it has, ends a wait between passes so that the run looks for issues at once with its back-off from the first step, and answers with a `runs` message that holds the `id` of the start. A stop that a person asked for gets an `error` message `the run is stopping`;
- sends every client the progress of every run when it connects and on every change, as `{ "type": "runs", "runs": { "<path>": {...} } }`. The progress of a run holds only its `status` (`running`, `stopping`, `finished`, `stopped` or `failed`), `hunting`, `watching`, `issues`, `upgrade` while it stops for an upgrade (see below), `hunt` (`true`) while a hunt runs, from its `hunt.start` to its `hunt.end` event, and `error` when it failed. `issues` holds one `{ "issue": <number>, "step": "<step>" }` entry per running issue, and is empty when no issue runs. The `step` is `implementing`, `reviewing` (with the review `round`), `fixing` (a fix of review findings, failed checks or a commit hook), `landing` or `waiting-for-checks`. It has no `step` until its first of these starts, and keeps its last step during other work, such as local checks. Each change of a step sends a new `runs` message. An issue leaves the list when it ends, whatever its outcome. The hunter adds no entry; `hunting` is the on/off setting, and `hunt` shows a hunt that runs. A run that ends with an error, such as a failed read of the open issues, is `failed` even when it was stopped;
- sends every client `{ "type": "output", "root": "<path>", "text": "<lines>" }` for each line of output of a run, as the run prints it. The same lines still go to `.next-issue/worker.log`. A client that falls more than 8 MiB behind, for example `next-issue logs` suspended with Ctrl-Z, is disconnected, and the other clients keep getting the output;
- sends every client `{ "type": "pass", "root": "<path>", "summary": {...} }` after each pass of a run started with watching on that handled an issue, with the summary of that pass;
- sends every client one `{ "type": "end", "root": "<path>", "code": <n>, "summary": {...} }` message when a run ends. `code` is 1 when an issue needs a person or failed and 0 when it does not, and `summary` is the summary of the whole run, as in `<id>.summary.json` (in a watch run, all passes). A run that fails has `code` 1, no `summary`, and the reason of the failure in `error`, which the worker also writes to `.next-issue/worker.log` as `<reason>`;
- stops a run when a client sends `{ "type": "stop", "root": "<path>", "after": "issue" | "round" | "now" }`. With no `after`, it stops after `issue`. `issue` means no new claim or hunt, and the held issues and a going hunt finish. `round` means each running issue stops after its current round, with the state kept, and a going hunt ends first. `now` stops every agent, command and hunt of the run at once, and each running issue ends as `stopped` with its state and labels kept; the run then ends, and so does the worker, as when any run ends. A later point than one already asked for changes nothing, and an earlier one replaces it. An unknown `after` gets an `error` message. While a run is going, the client that sent the stop gets `{ "type": "stopping", "root": "<path>", "waiting": <bool>, "hunting": <bool> }`, with the `id` of the stop when it has one: `waiting` is `true` when the run waited between passes, and `hunting` is `true` when a hunt was going, whether the run waited or worked on issues;
- switches watching of a run on or off when a client sends `{ "type": "watch", "root": "<path>", "on": true | false }`. The run keeps its issues, worktrees and progress, and nothing restarts. A run starts with watching on, unless it was started with `--watch off`. On keeps the run going after the current pass, as with `--watch on`. The client that sent the switch gets a `runs` message with the `id` of the request once the switch is made. On for a run that a person asked to stop gets an `error` (`the run is stopping`, with the `id` of the request) and changes nothing; on for a run that stops for an upgrade keeps the upgrade, so the run is still resumed. Off ends the run after the current pass, or at once when it waits between passes, and also turns hunting off. With no run going, the message gets an `error` and starts nothing;
- switches hunting of a run on or off when a client sends `{ "type": "hunt", "root": "<path>", "on": true | false }`. The run keeps its issues, worktrees and progress, and nothing restarts. Every run of the worker has a hunter: a run started with `--hunt on` starts with hunting on, and any other run with it off. Off lets a hunt that is going finish, so the issues it files stay, and starts no new hunt. On wakes the hunter at once, with no back-off wait, and also turns watching on. The client that sent it gets the same `runs` answer as for watch, and on for a run that a person asked to stop gets the same `error` as watch on. With no run going, the message gets an `error` and starts nothing. The settings last for the run only: a new run takes them from its own flags. The progress of each run carries `hunting`, `true` while hunting is on, and `watching`, `true` when the run watches for issues;
- exits, and removes its socket and lock files, when a run ends, after it sends the `end` message, even while a client is connected. It waits at most 5 seconds for that send, so a client that stops reading does not keep it open. Once a run ends, or once it begins to close for any other reason, it refuses every start of a new run with `the worker is shutting down, try again soon`. Before its first run, it exits when no client is connected, or when no client connects in the 30 seconds after it starts;
- waits up to 5 seconds for the lock when a worker that is closing still holds it;
- closes once no run is going when a client with a newer version connects, so that the client can start the newer worker. When a run has ended but the worker is still sending its `end` message, it first finishes that send (within the same 5 seconds), so every connected client still gets `end`. The `hello` of a client can say how to start the worker of its version, as `"launch": { "command": "<command>", "args": ["<arg>", ...] }`, such as `npx -y next-issue@<version> serve`; `npx -y next-issue@latest start` sends its own `node <script> serve`. A run that watches is stopped between issues for that, as `stop` with `issue` does: it claims nothing new, and its running issues and its current hunt finish. Its progress then holds `"upgrade": { "from": "<worker version>", "to": "<client version>" }`, with `"resumes": true` when the first newer client gave a `launch`. A stop by a person, or turning watching off, drops that field, so the run does not start again. Turning watching off also takes back the stop for the upgrade, so the run claims and works the rest of the current pass and then ends as `finished`, with no `run.stop` in its run log, even when some of its running issues ended before; a stop that a person asked for still holds. With `resumes`, once the run ends, the worker stops listening, runs that command in the repository with its output in `.next-issue/worker.log` (or uses a worker that already listens there), waits up to 2 minutes for it to listen, since `npx` may first download it, and asks the newer worker to start the run again with the same `--watch` and `--hunt` settings, before it closes. This works with no client connected. When the newer worker does not start or does not start the run, the worker writes the reason to `.next-issue/worker.log`, and its clients see the run `failed` with an `error` that starts with `the worker could not start next-issue <version>`. Without `resumes`, a client starts the newer worker and the run again. A run that fails while it stops for an upgrade ends `failed` and is not started again on the newer worker. A run that does not watch is left alone. Meanwhile the worker refuses every start of a new run with `the worker is restarting, try again soon`. A `start` with `"resume": true` gets no error when the worker refuses it;
- asks npm for the latest `next-issue` version (`https://registry.npmjs.org/next-issue/latest`) before a run claims each issue, with a 3-second limit. When npm serves a newer version than the worker, it upgrades the run as for a newer client with a `launch` of `npx -y next-issue@<version> serve` (`"upgrade": { "from": "<worker version>", "to": "<npm version>", "resumes": true }`), even when the run does not watch: the run claims no new issue, its running issues finish, and it starts again on the newer worker with its own `--watch` and `--hunt` settings, so a run with watching off still ends after its pass. Turning watching off while the run stops for such an upgrade cancels it for the rest of the run: the run claims and works the rest of its pass, ends `finished` and is not started again on the newer version; it does not upgrade until watching is turned back on. When a newer client connected before, its version and `launch` decide the upgrade instead: the run upgrades to the client's version, and when that client gave no `launch`, the upgrade has no `resumes`, so the run stops, even when it does not watch, and the worker does not start it again. When npm cannot be reached, is slow, answers with an error or serves the same or an older version, the run claims the issue as before. The check is always on;
- stops every agent and command and exits on `SIGTERM`, `SIGHUP` or `SIGINT`, and removes its socket and lock files only after its commands have stopped, including clean-up commands it starts after the signal, just before it exits. A command that is still running 10 seconds after the signal gets `SIGTERM`, and 10 seconds later `SIGKILL`; this includes a clean-up command started after the signal, and one still running after those 20 seconds gets `SIGKILL` every 10 seconds. The worker exits at the latest 10 seconds after every command has had `SIGKILL`, so no second worker starts while it still undoes steps in a worktree;
- writes `worker.start` with `version`, `pid` and `socket` to `.next-issue/worker.log` once it listens, and `worker.exit` with `reason` and `code` as it exits, both as `HH:MM:SS kind key=value` lines like the run output. `reason` is `idle` (a run ended, or no client and no run was left), `upgrade` (closing for a newer client, with `to=<version>`), `hand-over` (it passed its run to the newer worker), `hand-over-failed` (the newer worker could not start, so the run failed), `SIGTERM`, `SIGINT`, `SIGHUP` or `crash`. `code` is 0, 128 plus the signal number (such as 143 for `SIGTERM`), or 1 for `hand-over-failed` or a crash. Both have `error=<message>`, and a crash also has the full stack on the lines below. The worker exits with that code. When a run is going as it exits, `worker.exit` also goes into the run log of that run, so `npx -y next-issue@latest logs` shows it. A worker that finds another worker holding the lock writes only `another worker is running`. A worker killed with `SIGKILL` writes no `worker.exit`;
- writes `worker.error` with `error=<message>` to `.next-issue/worker.log` when its server reports an error after it listens, such as `EMFILE` when it cannot accept a connection, and goes on with its run;
- keeps `.next-issue/worker.log`, where a client that starts the worker writes its output, within 10 MiB: once it holds the lock and then once a minute while it runs, it cuts a log of more than 10 MiB to its newest 5 MiB, from the start of a line. It skips the cut while a command that writes to the log runs. A worker that finds the lock held only appends its own lines. The run logs under `.next-issue/runs/` hold the same events.

`npx -y next-issue@latest stop` asks the run that is going in the worker of this repository to stop after its current issues: it sends the worker `{ "type": "stop", "root": "<path>", "after": "issue", "id": "<id>" }`, prints what the run waits for and exits with 0 without waiting for the run to end. The run claims no new issue, finishes the issues it holds and ends. It reads the running issues from the progress of the run and whether a hunt is going from the `stopping` reply, and prints:

- `the run stopped` when the run waits between passes with no hunt going;
- `the run is stopping` when no issue runs and no hunt is going while the run is in a pass, such as when it reads the open issues;
- `the run will stop after #12, #15 and #16`, naming every running issue, when no hunt is going;
- `the run will stop after its current hunt` when a hunt is going and no issue runs;
- `the run will stop after #12, #15 and its current hunt` when both are.

When the worker sends no `stopping` reply within 5 seconds, as an older worker does, it prints `the run will stop after its current issues`. When the run stops for an upgrade, it sends the same `stop`, which drops the upgrade, so the run is not started again on the newer worker, and the line ends with ` and not start again`, such as `the run will stop after #12 and not start again`, or with ` and will not start again` after `the run stopped` or `the run is stopping`. When a person asked the run to stop already, it prints `the run is stopping already`. When no worker or no run is going, it prints `no run is going in this repository`. In these two cases it sends nothing and starts no worker. It never sends a signal to the worker, and workers of other repositories carry on.

`npx -y next-issue@latest status` shows the run that is going in the worker of this repository. It prints `<status> in worker <version>`, where the status is `running` or `stopping` (a stop by a person or for an upgrade), then `watching on|off, hunting on|off`. While the run stops for an upgrade, it prints `stopping for an upgrade to <version>`. It then prints one line per running issue with its number and step, such as `#624 reviewing (round 2)` or `#626 waiting for checks`; an issue whose first step has not started yet shows as `starting`. With no running issue, a running run prints `looking for an issue` while the worker fetches the issue list, checks for an upgrade or checks an issue before it starts, and `looking again in <n> minutes` (the minutes left, rounded up) while the watch waits before its next pass; otherwise it prints `no issue is running`. While a hunt runs, it prints `hunting for bugs` last, after the issue lines or the idle line; it prints no such line while no hunt runs, even with hunting on. When no worker or no run is going, it prints `no run is going in this repository`. It exits with 0 in every case, sends nothing that changes the run and starts no worker.

## Development

See [Develop](https://github.com/ravshansbox/next-issue#develop) in the root README for the scripts.

`npm run build` empties `dist`, then compiles `src/**/*.mts` to `dist/**/*.mjs`, so no file of an older build is left there. `src/cli.mts` is the entry point; `src/cli/` holds the client-only code, `src/worker/` the worker-only code and `src/shared/` the code both use. The package holds the compiled files, because Node does not strip types under `node_modules`.

## Releases

Releases are automatic and need no pull request. Push a [conventional commit](https://www.conventionalcommits.org/) to `main`. The workflow reads the commits since the last tag and picks the bump: `feat` gives a minor, `fix` gives a patch, and a `!` mark or a `BREAKING CHANGE` body gives a major. Any other type releases nothing. The notes of the GitHub release list the subject and short hash of each breaking, `feat` and `fix` commit since the previous tag, grouped by type, and end with the compare link from that tag.

The release is the `release` job of the `ci` workflow, and it runs only after the `check` job of the same commit passes. A commit that fails the typecheck, lint, format check, tests or build releases nothing. As the release is part of the `push` run, the harness waits for it like any other check. Release jobs run one at a time, in the order their `check` jobs finish, which is not always push order. When a later commit releases first, its tag holds the earlier commit and its version counts the commits of both, so the release job of the earlier commit only repairs and does nothing else.

The workflow then gives `next-issue` the new version and publishes it to npm with a [trusted publish](https://docs.npmjs.com/trusted-publishers), so no token is stored. It pushes the tag before the publish and makes the GitHub release after it, so the next release always counts from the new tag and never tries to publish a version that npm already holds, and no release job counts from a tag before one that already holds its commit. npm makes a new version live a few minutes after the publish, and not always in the order it got them, so before it publishes, the job waits until npm serves `next-issue` at the version of the last tag, for up to 10 minutes. Thus a new version never goes live before the one that came before it. Every run first repairs the last tag before its own commit: from a checkout of that tag it publishes each package that npm does not serve at the tag version, and makes the GitHub release if it is missing. A package that npm refuses as a version it already holds, but does not serve yet, counts as published. So when a step fails after the tag push, the next run of a later commit finishes that release before it makes a new one. The release job of an earlier commit that runs after it does not, as it repairs the tag before its own commit. To repair a release without a new commit, run the `ci` workflow by hand; after the checks pass, the release job only repairs and does nothing else. The release job installs with `npm ci --ignore-scripts`, so no install script of a dependency runs with its rights to push and publish. Its actions are pinned to commit SHAs. The publish runs no typecheck and no tests, as the `check` job has run them. So a failing test cannot stop a publish after the tag push. Do not publish by hand: its `package.json` holds version `0.0.0`, and only the release job sets the real version. Use the `ci` workflow run above instead.

The job uses the npm that comes with Node 24 and never installs another one. Trusted publishing needs npm 11.5.1 or later, so the job stops with an error before anything else when the bundled npm is older. The release job stays on a GitHub runner, because npm takes provenance only from a GitHub runner.
